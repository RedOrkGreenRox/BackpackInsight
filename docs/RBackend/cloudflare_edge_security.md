# Cloudflare edge proxy and API secret

## Main rule

A secret delivered to browser JavaScript is not a secret. Any header, token, encrypted blob, or derived value that the browser must attach to requests can be copied and replayed by the user.

Therefore `API_SECRET` / `ROOT_API_SECRET` must stay server-side:

- Cloudflare Pages Function / Worker reads it from environment variables;
- the browser calls `/api/*.fb` on the Cloudflare domain;
- the edge function adds `X-Internal-Secret` while proxying to the VPS;
- the browser never receives this header value.

## About “encrypt session id with my key”

This can authenticate a token format, but it does not hide usable credentials from the browser if the browser receives the token.

Possible variants:

- token generated in browser from a public session id + public code: not secure, attacker can generate it too;
- token generated by server and sent to browser: attacker can copy/replay it until expiry;
- short-lived HMAC/JWT per session: useful for rate limiting or CSRF-like flow control, but not a replacement for a server-side secret.

## Recommended protection layers

1. Keep `API_SECRET` only in Cloudflare edge env and backend env.
2. Backend validates `X-Internal-Secret` in constant time for protected binary API routes.
3. VPS firewall should ideally allow backend port only from Cloudflare IP ranges or from the reverse proxy layer. If the port must remain public, the secret still blocks casual direct access, but firewalling is stronger.
4. Do not put `API_SECRET`, derived permanent tokens, or encryption keys into frontend bundles.
5. For user-specific state later: use normal server-issued session cookies (`HttpOnly`, `Secure`, `SameSite`) or short-lived signed session tokens, but treat them as user auth, not as the internal backend secret.

## Current edge state

`Frontend/Web/functions/api/[[path]].ts` now proxies only:

- `GET /api/items.fb`;
- `GET /api/catalog-summary.fb`;
- `GET /api/sitemap`;
- `POST /api/profile.fb`.

It whitelists request headers, injects `X-Internal-Secret` from Cloudflare env server-side, and returns text errors instead of JSON compatibility error bodies.

Frontend-owned Cloudflare Functions were restored so Cloudflare Pages deployment does not lose route files. The sitemap function now proxies RBackend `/api/sitemap`; item route functions no longer fetch deleted `/api/items` JSON and only keep SPA routing alive until the new FlatBuffer middleware/frontend lands.
