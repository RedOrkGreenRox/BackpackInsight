# Backend optimization notes — заметки для будущей декомпозиции

Этот файл — отдельная записка, чтобы не потерять важные наблюдения при переходе к корневой Rust-системе.

## 1. Backend можно заметно оптимизировать

В текущем backend много логики работает корректно для текущего приложения, но архитектурно может быть оптимизировано после декомпозиции игровой модели:

- расчёт уровня игрока;
- расчёт XP предметов;
- пересчёт статистики профиля;
- поиск и сопоставление предметов;
- синхронизация справочника предметов с БД;
- формирование frontend response;
- повторяющиеся преобразования JSON/ORM/cache.

## 2. Расчёт уровня сейчас считается совместимо, но не считается истиной

Текущая формула уровня переносится в `core` только как совместимый слой с текущим backend.

Важно: пользователь уточнил, что расчёт уровня **вероятно неверен**. Правильный расчёт должен появиться позже, когда сама игра будет декомпозирована и станет понятно, как именно считать уровень.

Поэтому правило:

```text
LevelService сейчас = compatibility layer
будущий GameLevelService = настоящая игровая формула после декомпозиции игры
```

Нельзя считать текущий `LevelService` окончательной игровой истиной.

## 3. Тестов должно быть как можно больше, но не в deploy artifact

Тесты нужны для агента и разработки:

- unit tests;
- snapshot tests;
- property tests;
- fixture tests;
- compatibility tests против текущего Python backend;
- data validators;
- image validators;
- budget checks.

Но тесты не должны попадать в production/deploy artifact.

Для Rust это означает:

```text
cargo test / dev dependencies / test fixtures — только dev/CI
release binary / wasm islands / FlatBuffers packs — без тестового мусора
```

Для Docker/production позже нужно явно следить, чтобы:

- test fixtures не копировались в runtime image без необходимости;
- `target/debug` не попадал в образ;
- dev-only CLI/bench/fuzz не попадали в минимальный production image;
- debug symbols и source maps не уходили в production, если они не нужны.
