# Требования к работе в репозитории BackpackInsight

Единый свод правил для людей и ИИ-агентов. Заменяет `ARENA.MD`. Если правило здесь расходится с другим документом, верно это.

## 1. Порядок работы: документация, контракты и тесты, код, сверка

Для новой функции, нового модуля или изменения поведения шаги идут строго по порядку, каждый отдельным коммитом (коммиты можно пушить вместе):

1. **`spec(<область>): …`: описание до кода.** В `docs/` пишется или обновляется документ функции (индекс модуля или документ входного файла): назначение, поведение, контракты (маршруты, параметры URL, публичные типы, трейты и сигнатуры, форматы данных) и пронумерованные критерии приёмки в разделе «Планируется». Если задача пришла из дизайна владельца, домыслы помечаются как допущения и показываются ему; работа идёт дальше по частям, которых они не касаются.
2. **`test(<область>): …`: тесты из критериев.** Каждому проверяемому критерию соответствует тест. Для чисто визуального поведения тестируется логика состояния, а ручная проверка записывается списком в описании. На старом коде тесты падают или не компилируются.
3. **Код**, пока тесты не пройдут, вместе с `cargo clippy` без предупреждений.
4. **Сверка.** Зеркальные документы всех затронутых файлов описывают код как есть; сделанное убирается из «Планируется»; отступления от описания записываются с причиной. Перед пушем: тесты и `python3 scripts/check_docs.py` без новых ошибок и предупреждений.

**Мелкие правки** (исправление ошибки, стиль, до 2 файлов, без нового контракта) пропускают шаги 1–2, но зеркальные документы обновляются в том же коммите.

Зеркальные документы на файлы, которых ещё нет, заранее не пишутся: описание до кода живёт в документе функции, зеркала появляются на шаге 4.

## 2. Сетевая документация

- **1:1.** У каждого исходника под git (`.rs`, `.py`, `.ts`, `.js`, `.scss`, `.sql`, `.mako`, `.fbs`, `Cargo.toml`, `rust-toolchain.toml`) есть зеркальный документ `docs/<путь без расширения>.md` (`Cargo.toml` → `Cargo.toml.md`). Исключения: `generated/`, `target/`, данные (JSON), бинарные ассеты, сами `.md`.
- **Оформление.** H1 ведёт на исходный файл; есть раздел «Назначение»; в конце подпись `> 📌 **Подпись документации:** …` с датой сверки или источником генерации.
- **Только текущее состояние.** Основной текст описывает то, что есть в коде. Планы живут только в разделе «Планируется».
- **Ссылки вместо копий.** Логику соседнего модуля не пересказывают, а ссылаются на его документ: `[Название](путь.md)`. Каждый документ достижим по ссылкам из `README.md` или `docs/structure.md`.
- **Расхождение кода и документа — ошибка.** Её исправляют сразу: код или документ, чтобы осталась истина.
- **Проверки.** `scripts/check_docs.py` (в CI `docs.yml`) проверяет ссылки, сирот, свежесть `docs/structure.md`, зеркала, оформление, покрытие символов и символы, которых нет в коде. Подробно: [check_docs](docs/scripts/check_docs.md).
- **Хук.** В каждом клоне и worktree один раз: `git config core.hooksPath .githooks`. Хук перед коммитом обновляет `docs/structure.md` и граф документации.

## 3. Размер файлов

| Уровень | Строк | Когда |
|---|---|---|
| Желательно | до 80 | всегда |
| Пограничный | до 150 | сложный модуль, если деление ухудшит чтение |
| Крайний | до 250 | только с обоснованием в документе файла |

Файл больше 150 строк делят по ответственности, а не механически. Правило касается и `.md`. Исключения: сгенерированные файлы, `docs/structure.md`, `README.md`, этот файл. Старый фронтенд сверх лимита учтён в [журнале](docs/oversized_frontend_files.md).

## 4. Код

- **Стек.** Всё на Rust: сервер Axum, интерфейс Leptos (SSR + islands). TypeScript только в крайнем случае.
- **Строгость.** Rust и TS на максимальной строгости с линтерами; clippy без предупреждений. DRY, SRP, модульность и DDD там, где они уместны.
- **Дендритная архитектура** (крейт `RBackend/crates/branches`): `roots/` содержит реестр маршрутов, оболочку, `Branch`, `BranchSpec` и `BranchRunner`; `branches/<страница>/` содержит страницу, разделённую по ответственности (`branch`, `card`, `manager` для острова, `url`, `*_fn` для чистых функций); `shell/` содержит общий каркас. У всех страниц одинаковая форма `<head>`.
- **Тесты.** Новые маршруты, модели и сервисы покрываются тестами; юнит-тесты лежат рядом в `<модуль>_tests.rs`.
- **Git.** Окончания строк LF (`.gitattributes`); `.env` и секреты не коммитятся.

## 5. Требования к продукту

- Сохраняется существующий дизайн (боковое меню, главная «Profile Showcase» с зоной загрузки экспорта). Переделка только по просьбе владельца.
- Ни один элемент управления не перезагружает и не перерисовывает всю страницу: обновляется только то, за что он отвечает. Смена языка ненадолго размывает текст и подменяет его на месте.
- Названия предметов не переводятся: в любой локализации они на английском, как в игре.
- Исходные ContentKit игры не изменяются: все исправления лежат в отдельном файле правил, который применяет сборщик.
- Сайт работает за Cloudflare Pages (`*.pages.dev`), бэкенд за прокси с `X-Internal-Secret`.
